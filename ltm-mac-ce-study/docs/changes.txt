[2026-08-27] STEP 4 DONE — baseline LTM-style fast MAC-triggered handover + near-zero

WHAT WAS BUILT
- Mobility fix (carried over from the interrupted prior instance, verified here): UE mobility
  is a constant-SPEED distance-mode RandomWalk2d (1000 m straight legs, wall bounces) so UEs
  actually traverse cell edges. At 60/120 km/h over a 250 m-ISD grid this needs ~8-15 s of sim
  before the first edge crossing (a 60 km/h UE moves only ~33 m in 2 s), which is why short
  (<=2 s) runs show 0 handovers — expected geometry, not a bug.
- Fast MAC-triggered handover proxy (boundary B1): a periodic (20 ms) A3-like checker
  (HandoverCheck) fires NrHelper::HandoverRequest(0 ms, ue, srcGnb, targetCell) when a
  neighbour is closer than the serving cell by a distance hysteresis, sustained for the 320 ms
  time-to-trigger. HandoverStart/EndOk/EndError RRC traces are hooked per UE.
- Interruption is now reported TWO complementary ways (both no-attack baseline):
    (1) CELL-SWITCH EXECUTION TIME = HandoverEndOk - HandoverStart. Measured = 2.036 ms
        (deterministic NR HO-procedure latency with 0-delay X2). This is the direct proxy of
        the intra-BS LTM ~1-2 ms "near-zero" cell-switch budget — the headline Step-4 KPI, and
        it lands squarely in the spec's target range.
    (2) DL DATA-PLANE INTERRUPTION = gap between last DL packet delivered before and first
        after the switch. Baseline ~13-42 ms (seed 1: mean 21.7 / median 13.8 / p95 41.9 ms;
        seed 2: mean 27.9 / median 17.1 / p95 83.9 ms). Larger than (1) because NR's X2 HO is
        NOT make-before-break/lossless (in-flight RLC PDUs on the source are dropped; the
        target re-establishes grants after attach). Documented as a B1-proxy property. Under
        the forged-switch attack this metric will balloon (RLF + RRC re-establishment ->
        hundreds of ms) — that is the DoS quantified in later steps; (1) stays ~2 ms or errors.
  A machine-readable RESULT_BASELINE line now emits hoEvents/hoFail, dp{Mean,Median,P95}Ms,
  sw{Mean,Median,P95}Ms, and per-direction DL/UL loss% and throughput for the sweep harness.

[2026-08-28] STEP 5 DONE — RLF/handover-failure tracing + re-establishment outage, and the
forged-mis-switch attack mechanism (Steps 8-9 core) rewired onto a 3GPP-faithful failure path
================================================================================
CONTEXT / WHY THIS TOOK ITERATION
The Step-5 goal is to make a forged mis-switch DELIBERATELY and RELIABLY produce a
failure -> RRC re-establishment outage, and to time it. The originally-scaffolded mechanism
(displace the victim into "coverage loss" so nr's radio-link-monitoring emits out-of-sync
indications -> N310 -> T310 -> RadioLinkFailure) did NOT fire in this scenario. Systematically
ruled out as causes (each tested on real runs): RLF timers (N310/N311/T310, incl. 1/1/1000ms),
ThreeGppChannelConditionModel UpdatePeriod, ThreeGppChannelModel (matrix) UpdatePeriod,
displacement magnitude (1.5-20 km), and scheduler (default vs round-robin). nr's own
radio-link-failure test triggers RLF with an identical SetPosition jump, but reproducing it here
would require porting nr's whole RLF-test scenario config (scheduler, Shannon AMC, noise figures,
UL power control, fixed-LOS channel), which risks perturbing the validated Step 3/4 results.
Per the user's directive ("do the option that's more realistic and accurate, based on the thesis
and 6G 3GPP"), switched to the mechanism that is BOTH more faithful and robust.

MECHANISM ADOPTED — nr's real HANDOVER-FAILURE path (3GPP-emergent, not scripted)
A forged LTM cell-switch carries a spoofed Target Configuration ID: the UE is commanded to switch
to a target it cannot actually complete access to. Realised with nr's own handover-failure
machinery (contrib/nr/test/nr-test-handover-failure.cc): the victim is commanded (via
NrHelper::HandoverRequest) to a REAL neighbour cell, but that target's RACH preambles are dropped
for the duration (NrGnbPhy TestDropRachPreambles), so the UE exhausts PreambleTransMax ->
HandoverFailureMaxRach (a DURING_HANDOVER failure) -> it falls back to RRC re-establishment
(CONNECTED_PHY_PROBLEM -> IDLE cell search -> reconnect) on a reachable cell. The RACH drop is
scheduled off 1.5 s later so later legitimate access to that cell is unaffected. This is the
emergent 3GPP RRC/RACH failure->recovery path, not a hand-scripted timeline. nr is UNMODIFIED
(model/ tree pristine); everything lives in the example.
- A HandoverRequest to a NON-EXISTENT cell id was tried first (most literal "spoofed target") but
  nr null-derefs the missing target gNB -> SIGSEGV, so a real-but-wrong target + RACH-drop is used
  instead. Documented as a modelling choice.

WHAT WAS BUILT/CHANGED (all in examples/ltm-forged-handover.cc; nr core untouched)

- Rewrote the Step-5 controlled RLF probe (--rlfProbeUe/--rlfProbeTimeMs): was a handover to the
  farthest cell (nr completes it successfully -> no failure); now names a real neighbour + drops

- Rewrote the Step-9 attacker landed-forge branch (DoOpportuneSwitch): replaced the non-firing

  decision still draws from the §6 P(forge-decode) table (Step 8), unchanged.

[2026-08-28] LTM IMPLEMENTED — real air-interface 6G LTM cell-switch MAC CE in nr core
================================================================================
User directive: replace the LTM *proxy* (a direct NrHelper::HandoverRequest call) with a
genuine 6G LTM Lower-layer-Triggered-Mobility cell switch delivered as an unauthenticated
Layer-2 MAC Control Element on the real air interface, with the attacker forging it at the PHY.
Chosen fidelity (user pick): "Full air-interface MAC CE in nr core" (the deepest option).
nr v5.1 has NO native LTM (nor conditional handover), so this was built from scratch across
nr's PHY/MAC/RRC. nr core is now MODIFIED (previously pristine) — this is our clone.

WHAT WAS BUILT (nr core, 9 files + example)
- New control message NrLtmCellSwitchMessage (model/nr-control-messages.{h,cc}) + a new
  NrControlMessage::LTM_CELL_SWITCH type. Carries unicast RNTI, targetCellId, Target
  Configuration ID, and a "forged" tracing flag. It is a real DL control-channel message
  (below PDCP, unauthenticated) — the exact artefact the thesis says is forgeable.
- gNB emit: NrGnbPhy::SendLtmCellSwitch(rnti,targetCellId,targetConfigId) builds the CE, stamps
  the source BWP ARFCN, and enqueues it on the DL control channel with EnqueueCtrlMsgNow (no
  extra latency — the LTM design point). (model/nr-gnb-phy.{h,cc})
- UE receive/dispatch: NrUePhy::PhyCtrlMessagesReceived gains an LTM_CELL_SWITCH branch that
  checks the CE addresses this UE's RNTI (unicast) and relays it up via the CPHY SAP.
  (model/nr-ue-phy.cc)
- CPHY SAP: new upcall NrUeCphySapUser::RecvLtmCellSwitch(...) + MemberNrUeCphySapUser
  forwarding to the RRC (model/nr-ue-cphy-sap.h).
- UE RRC: NrUeRrc::DoRecvLtmCellSwitch(...) acts on the command (the UE cannot authenticate it,
  so legitimate and forged commands are handled identically — the vulnerability) and fires a new
  "LtmCellSwitchReceived" trace source (imsi,cellId,rnti,targetCellId,targetConfigId,forged).
  (model/nr-ue-rrc.{h,cc})
- Attacker PHY injection: NrUePhy::InjectForgedLtmCellSwitch(targetCellId,targetConfigId) feeds a
  forged CE straight into the victim UE's DL-control receive path — the capture-effect overshadow.
  (model/nr-ue-phy.{h,cc})
- Example rewire (examples/ltm-forged-handover.cc): the A3-like checker now, instead of calling
  HandoverRequest, EMITS the LTM MAC CE — legitimately via gNB SendLtmCellSwitch to the best
  cell, or, when the attacker's §6 capture draw lands for a victim, via the victim UE's
  InjectForgedLtmCellSwitch with a spoofed target. When the UE acts on the CE (LtmCellSwitchReceived
  trace) the example executes the mechanical switch (LtmExecuteSwitch), reusing nr's tested
  handover: a legit target completes fast; a forged/spoofed target has its RACH dropped so the
  handover fails -> RRC re-establishment (the DoS).

[2026-08-28] ACCURATE LTM — candidate pre-configuration + Target-Config-ID activation (not L3 reconfig)
================================================================================
Reviewer (supervisor) critique, grounded in handover_6g.pdf (3GPP Rel-20/21 study): the prior
build delivered a real MAC-CE trigger but EXECUTED a full L3 X2 handover at switch time -- i.e.
a MAC-CE-triggered classic handover, not LTM. Real LTM (handover_6g section 15.2 scheme 2 /
section 9.2): the network pre-configures candidate cells IN ADVANCE, the UE pre-parses them, and
the cell-switch MAC CE merely ACTIVATES a candidate by its Target Configuration ID -- "execution
is an activation rather than a reconfiguration."

WHAT WAS CHANGED (nr core + example)
- NrUeRrc now holds an LTM candidate table m_ltmCandidates (Target Configuration ID -> candidate
  cell) with a public AddLtmCandidate(configId, cellId). Models the candidate configuration the
  serving cell delivers in advance over RRC. (model/nr-ue-rrc.h/.cc)
- NrUeRrc::DoRecvLtmCellSwitch no longer just logs: it LOOKS UP the Target Configuration ID among
  the pre-configured candidates. A valid id ACTIVATES that candidate; an id with no candidate
  (exactly what a forged/spoofed Target Configuration ID carries) has nothing valid to activate.
  The LtmCellSwitchReceived trace gained a validCandidate flag (now 7 args).
- Example: at setup each UE is pre-configured with a candidate per real cell (configId==cellId)
  via AddLtmCandidate -- the "config file sent beforehand". The legitimate switch names a valid
  candidate's config id (activation). The attacker now injects a SPOOFED config id (50000+cell)
  the victim has NO candidate for -> activation impossible -> the UE attempts an unprepared switch
  and fails (RACH) -> RRC re-establishment (DoS). This replaces the earlier RACH-drop-as-attack
  with the faithful "spoofed Target Configuration ID has no valid candidate" mechanism.

REAL VERIFICATION (actual output)
- Legit (4 cells, no attack): "LTM-RX UEx acts on LTM MAC CE configId=C -> ACTIVATE pre-configured
  candidate cell C [legit]"; 5 activations, 0 failures, switch-exec 2.00 ms. No crash.
- Forged (2 cells, forced @2s, 8 dB): "LTM-RX UE0 acts on LTM MAC CE configId=50001 -> NO
  pre-configured candidate (spoofed) cell 1 [FORGED]" -> DURING_HANDOVER failure -> re-establish;
  control-plane 240.0 ms, data-plane 262.4 ms. forgedLanded=1, recovered=1.

WHICH OF THE REVIEWER'S THREE POINTS ARE NOW ADDRESSED
1. Pre-configuration / network prepares in advance: YES -- candidate table pre-configured at the
   UE. (The AI/predictive-trajectory *decision* is still a geometric A3-like proxy; AI mobility is
   a separate study-phase 6G ambition, not part of LTM's switch mechanism.)
2. Network (gNB) issues the MAC CE, UE does not "ask": already correct; unchanged.
3. MAC CE activates a pre-stored candidate, not a fresh L3 reconfiguration: YES semantically --

REMAINING HONEST GAP (documented boundary)
- nr has NO RACH-less / early-TA activation path and no native prepare-and-hold of multiple X2

  ARCHITECTURE (pre-configured candidates + MAC-CE activation by Target Configuration ID +
